**中文**

CubSync 0.3.0 是它第一次有界面的版本 —— 桌面和手机都有。

下面三份下载，同一个版本号：**CubSync-0.3.0.msi** 装到 Windows；不想安装任何东西，
就取 **CubSync-v0.3.0-windows-x64.zip**；**CubSync-v0.3.0-debug.apk** 侧载到手机。
安卓用 debug 包是有意的：签名 release 需要一个 keystore，而 keystore 是「应用往哪儿分发」
的决定，不是构建步骤 —— 这件事定了再说。

---

## 这一版有什么

**桌面应用**（Compose Multiplatform）：连接、传输、同步、作业、日志、设置。
**安卓应用**：与桌面同一套说法；配置与作业各自成屏、带返回箭头，日志跟着它那次运行走 ——
手机上跑完一次，要问的是「这一次做了什么」。一个存储权限都不申请。

**双栏传输页**，两端都有：这边有什么、那边有什么、中间一支箭头。选中若干行，
或者什么都不选直接按箭头把看得见的全部送过去；复制走同步器用的同一套后端契约：
打开、按序写入、提交，最后才落时间戳。

**显示方式面板**，两端同一套：五种显示方式（紧凑 / 详细 / 卡片 / 缩略 / 对比）、
按百分比的行密度、网格档的列数、带「自动」的分栏方向（跟随容器形状）。

**同步引擎**（0.1 起就在，这一版起有界面）：比较与计划、分块传输与校验、断点续传、
冲突策略、镜像删除走回收站、过滤器。

## 一个版本，所有平台

在此之前 0.3.0 / 0.4.0 / 0.5.0 三个号各覆盖一个平台，因为功能是分批落地的。
它们描述的是同一个产品，所以现在是一个版本：一个 tag 从同一个提交构建出上面那三份产物，
同一个版本号，同一个发布页。

## 不是像素的那部分，只有一份源码

配置库、连接池、运行服务、文件夹服务、浏览会话、格式化器、应用日志都在 `service` 里，
两个前端驱动同一份。按钮点出来的同步与终端敲出来的同步是同一条代码路径 ——
当只有其中一半被真正试过时，这才是要紧的性质。

## 修掉

**`Files.readString` 与 `Files.writeString` 在 Android 上不存在** —— 它们是 Java 11 的新增，
API 37 的 `android.jar` 里也没有；在桌面 JDK 上编译通过，一到手机上第一次存配置就
`NoSuchMethodError`。**原子改名没接住 Android 抛的 `UnsupportedOperationException`**，
于是在对原子性没有意见的文件系统上每次写入都会失败。**安卓启动图标把标志也画进了背景层**，
与前景层同色的圆叠在一起，启动器上只剩一块蓝 —— 已修，背景回到纯色，生成脚本也改了。

## 还没像 demo 那样

demo 是一份完整规格，这一版是它的一部分。逐屏差在哪、按什么顺序补，
写在仓库的 `报告/规划/2026-10-16-后续规划与实施.md`。一句话：接下来是一串 0.3.x 补丁，
不升中版本号 —— 能力已经有了，只是还没照规格说清楚。

## 怎么验证

```
./gradlew check    # 303 项测试
```

两个进程走真实协议搬 1 GiB：校验和一致、没有残留暂存文件、第二次运行不做任何事。

**English**

CubSync 0.3.0 is the first release with an interface, on both a desktop and a phone.

Three downloads below, all the same version: **CubSync-0.3.0.msi** to install on
Windows, **CubSync-v0.3.0-windows-x64.zip** if you would rather not install anything,
and **CubSync-v0.3.0-debug.apk** to sideload on a phone. The APK is the debug build
deliberately: a signed release needs a keystore, and a keystore is a decision about
where the application is distributed rather than a build step.

---

## What is in it

**A desktop application** (Compose Multiplatform): connect, transfer, sync, jobs, logs,
settings.
**An Android application**: the same words as the desktop, with a configuration and a
job opening as their own screen and the log belonging to the run it came from, because
on a phone the question after a run is what *that* run did. No storage permission is
requested at all.

**The two-pane transfer browser**, on both platforms — the screen the design starts on:
what is here, what is there, and an arrow between them. Select rows, or press the arrow
with nothing selected to move everything visible, and the copy runs through the same
backend contract the synchroniser uses: open, write in order, commit, and only then
apply the timestamp.

**The display panel**, shared by both ends: five display modes (紧凑 / 详细 / 卡片 /
缩略 / 对比), row density as a percentage, column count for the grid modes, and the
three-way 分栏方向 with an 自动 that follows the shape of the container.

**The synchroniser** (there since 0.1, with an interface from this release): comparison
and planning, chunked transfer with verification, resume, conflict policies, mirrored
deletion through a trash folder, and filters.

## One version, every platform

Before this, 0.3.0, 0.4.0 and 0.5.0 each covered a single platform, because the features
landed at different times. They describe one product, so they are one version: a tag
builds all three artefacts above from the same commit, gives them the same number and
puts them on the same release page.

## One source for the parts that are not pixels

The configuration store, the peer pool, the run service, the folder server, the browse
session, the formatter and the application log live in `service`, and both front ends
are written against it. A sync started from a button and one started from a terminal
are the same code path — which is the property that matters when only one of them has
been tried.

## Fixed

**`Files.readString` and `Files.writeString` do not exist on Android** — Java 11
additions, absent from `android.jar` even at API 37, so they compiled on a desktop JDK
and would have thrown `NoSuchMethodError` on the first configuration save.
**A rename into place did not survive Android's `UnsupportedOperationException`**, so
every write would have failed on a filesystem with no opinion about atomicity.
**The Android launcher icon had the mark in both layers**, and the launcher showed a
single block of blue; the background is a plain colour again.

## Still not like the demo

The demo is a full specification and this is part of it. What is missing, screen by
screen, and the order it will be closed in, is in
`报告/规划/2026-10-16-后续规划与实施.md`. The short version: a run of 0.3.x patches.
No minor bump, because the capability is already there — it just is not described the
way the specification describes it yet.
